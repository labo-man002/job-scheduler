# Assumptions and modeling decisions

This is the "document assumptions and modeling decisions" item from issue [#27](https://github.com/taroryu004-lab/job-scheduler/issues/27)'s checklist. It covers both the class diagram ([docs/architecture.md](architecture.md)) and the database schema ([docs/erd.md](erd.md)).

## Modeling decisions

- **Topology is generalized, not fixed to a single 3D torus.** `node` stores a variable-length `coordinates` array instead of fixed `x/y/z` columns, and a new `cluster` entity carries `topology_type` (`TORUS`/`MESH`/`TREE`/`FLAT`, a lookup table), `dimension` (per-axis sizes), and `wrap` (whether an axis wraps — the property that makes a topology a torus rather than a plain grid). This replaced the earlier "config, there's only one cluster" approach once it became clear more than one cluster/topology shape needed to be representable, not just tunable dimensions on a single implied one.
- **Per-unit resource tracking over capacity counters.** `node_resource` gives each physical resource unit (a CPU core, a GPU) its own row with its own `resource_status`, instead of a `used_capacity`/`total_capacity` pair per node/resource-type. This makes "which exact unit is allocated to job X" a direct lookup instead of something inferred from arithmetic, at the cost of more rows.
- **Request and fulfillment are separate facts.** `resource_requirement` (what a job asked for) and `allocation_node` (what it actually got) are two different tables even though they reference the same `resource_type`. Collapsing them would lose the ability to audit "did the job get what it asked for."
- **Quotas, reservations, and usage are institute-level, not per-client.** `quota`, `reservation`, and `resource_usage` all key off `institute` (the same entity `client.institute_id` references), not `client` directly. An institute gets a resource ceiling and a usage history; individual clients within it don't get separate quotas.
- **`job_event` is an append-only log, not a state machine table.** `job.status_id` still holds current state; `job_event` exists purely to answer "what happened and when" (placement attempts, cancellations, status transitions) without needing to reconstruct history from `allocation` rows, which only reflect the current/final placement.
- **`Scheduler` and `Placer` are split by exactly one question each** — *when* vs. *where* — so `SortStrategy` and `PlaceAlgorithm` can be swapped independently without either class needing to know how the other decides (see "Where vs. when" in [docs/architecture.md](architecture.md)).
- **`Topology` and `TopologyView` are two objects, not one**, because `PlaceAlgorithm` needs to reason about occupancy (nearest/farthest `OCCUPIED` node) using data (`view`) that's cheap to rebuild on every placement attempt, while `Placer` is the only class that holds the authoritative node list needed to build it.
- **Persisted entities are enriched ORM models, not separate domain dataclasses.** `Node`, `ResourceNode`, `Cluster`, `Job` in `app/models/` carry the relationships/behavior (`Node.free_resources()`, etc.) that `Placer`/`Scheduler`/`Server` operate on directly — there's no parallel plain-Python `Node` class. Only logic with no persisted identity of its own (`Topology`, `PlaceAlgorithm`, `Placer`, `Scheduler`) lives as plain domain code.
- **No `AllocationRepository` class.** The class diagram in [docs/architecture.md](architecture.md) shows `Server` depending on a separate `AllocationRepository`, but every other persisted entity in this codebase is queried directly through the session rather than through a repository wrapper — adding one just for `Allocation` would be the only inconsistent spot. `Server` queries/writes `models.Allocation`/`models.AllocationNode` directly instead.
- **REST, not WebSocket, for the Client/Server boundary** (resolving the item below). All three commands (`submit_job`, `cancel_job`, `get_allocation_details`) are request/response with no server-initiated push, so plain REST is enough — `connect()`/`disconnect()` from the original class diagram are dropped.
- **One `Scheduler` per cluster, each a process-lifetime singleton; `Placer` is still rebuilt fresh on every drain.** `Server._schedulers` (a `cluster_id -> Scheduler` dict) means a job stuck waiting on one cluster never blocks a different job on a different cluster. Each is seeded once from `Job.status == QUEUED` on first use, then just `enqueue()`s new submissions in place (O(log N), no reload). `Placer` can't be shared the same way — it must hold *this* transaction's row-locked `Node`/`ResourceNode` objects, so it's still built fresh per drain, scoped to one cluster's nodes. The queue holds `PendingJob` (`app/domain/scheduler.py`: `job_id`+`priority`), never a live ORM `Job` — each request gets its own session, so a `Job` from a previous request's session would be detached garbage by the next. Cancelling a queued job doesn't remove its ref from the heap; `_drain_queue()` lazily discards it once dequeued if its DB status isn't `QUEUED` anymore (the standard `heapq` pattern for entries that can go stale) rather than needing a `Scheduler.remove()`. This is an explicitly single-process design — revisit if this ever runs multi-worker.
- **A `Job` never references a `Node`, `Cluster`, or topology — not even internally.** `Server` routes a job to the smallest cluster whose *total* capacity could fit it (`_best_fit_cluster`, by summed `ResourceNode` count), the same way `Placer` already picks a node without the job knowing. That routing decision is never persisted anywhere (no `cluster_id` column on `Job`) — it's recomputed deterministically (job size vs. current cluster capacities) both at submission and, after a process restart, when a cluster's `Scheduler` is first re-seeded. A job needing more than any cluster could ever hold, even empty, is a `JobTooLargeError`/`422` at submission time, not something left `QUEUED` forever. This also fixed a real bug: the original `_build_placer()` did `Cluster.query().first()` with no ordering, which could silently route a job against the wrong cluster whenever more than one existed (caught by accident while verifying persistence — see the conversation, not just theorized).
- **Row-level locking during placement.** `Server._build_placer()` locks every `Node`/`ResourceNode` row for the cluster (`SELECT ... FOR UPDATE`) before computing placement, so two concurrent requests can't both read the same free unit as available and double-allocate it. This serializes placement attempts against a given cluster; acceptable for now, revisit if throughput becomes an issue.
- **Draining stops at the first placement failure (strict priority order), not "place whoever fits."** Skipping a job that doesn't fit to place a lower-priority one that does is backfilling — an explicit, opt-in relaxation to build later, not the default behavior.
- **`Allocation.duration`/`end_time` are only known once a job stops running, not set at placement time.** A job whose duration is known upfront isn't a job, it's a reservation (already a separate concept in the schema). `Job.duration` is the client's estimate/hint (still useful later for backfilling), but `Allocation.duration` is computed from `end_time - begin_time` when the job completes *or* is cancelled — both go through `Server._end_running_job()`. This needed a migration (`Allocation.duration` nullable, `Allocation.end_time` added) and a new `complete_job`/`PATCH /jobs/{id}/complete` — the original ticket's 3 routes had no way for a job to ever reach `COMPLETED`.
- **`Quota` enforces a live concurrency cap, scoped to a calendar month via `period` — not a cumulative time-windowed usage figure.** `Server._check_quota()` reads it as "how many units of a resource type may an institute have `RUNNING` at once", counting current `AllocationNode` rows joined through to `RUNNING` jobs owned by that institute — but the *limit* it checks against comes from whichever `Quota` row's `period` falls in the current month, since an institute's limit can differ month to month (`period` names a month, it isn't a creation timestamp). No `Quota` row for the current month means unrestricted, same as no row at all. `Server.create_quota()` upserts: setting a limit for a month that already has a row updates it in place rather than creating an ambiguous second row. `resource_usage`/`consumed_hours` remain untouched — nothing in this codebase writes to that table, so a genuinely cumulative "X hours consumed this month" budget is a separate, unbuilt feature, not what `Quota` does here. Checked once per `submit_job`, before routing/queueing, so an over-quota request is rejected (`QuotaExceededError`/403) rather than silently queued forever.
- **Reservations narrow a job's candidate nodes per-institute; `Placer` itself stays reservation-agnostic.** `Server._reserved_node_ids(cluster_id, exclude_institute_id)` finds nodes currently reserved by a *different* institute, and `_drain_queue` filters `placer.nodes` down to the non-excluded set before each `attempt_placement()` call — two queued jobs from different institutes can have different rights to the very same cluster at the very same moment, which `Placer` (one cluster, no institute concept) has no way to represent on its own.
- **`create_reservation` requires an explicit `cluster_id` and rejects conflicting reservations; it never touches a currently-RUNNING job.** `cluster_id` is technically derivable from the node_ids alone, but requiring it catches the caller's mistake early (a node from the wrong cluster is a `NodeNotInClusterError`/422, not a silently-wrong reservation). Two different institutes reserving the same node for an overlapping window is rejected (`ReservationConflictError`/409) — without this, both institutes would see the node as reserved-by-someone-else and exclude it, making it unusable by anyone, a silent deadlock rather than a resolved conflict. The same institute re-reserving its own node is fine (not a conflict). If a node already has a RUNNING allocation from a different institute when the reservation is created, nothing preempts it: the reservation only governs future placement decisions, and takes effect once that job naturally completes/is cancelled and the node frees up -- consistent with strict-order draining never backfilling or displacing anything either.
- **`job_event` is populated from `Server`, one row per status transition** (`QUEUED` on submit, `RUNNING` on placement, `CANCELLED`/`COMPLETED` on `_end_running_job`), each with a short human-readable `comment`. Paired with plain stdlib `logging` (`app/logging_config.py`) for lifecycle/rejection lines an operator would tail live -- not a second persisted record of the same thing. `job_event` is the queryable permanent record; logs are ephemeral. Rejections (`QuotaExceededError`, `JobTooLargeError`) are logged but don't get a `job_event` row, since the job was never accepted in the first place.
- **`POST /institutes`, `POST /clusters`, `POST /quotas`, `POST /reservations` -- minimal setup/admin endpoints, added because without them the quota/reservation enforcement above had no way to be exercised outside a test.** `POST /clusters` takes an explicit per-node list (`NodeSpec`: `coordinates` + `list[ResourceCount]`, both plain dataclasses in `app/domain/server.py` -- not raw tuples, same reasoning as `PendingJob`) rather than auto-generating a grid from `dimension` -- auto-generation is a bigger, separate design question (sparse grids, partial fill) left for whenever it's actually needed. No auth/authorization on any of these yet -- anyone can register an institute or set anyone's quota; out of scope until there's an actual notion of an authenticated caller.
- **Cluster shape is validated at `POST /clusters` time, as an admission policy on `Server.create_cluster` -- deliberately NOT a `Cluster` model invariant.** `_validate_cluster_shape()` (`app/domain/server.py`, called only from `create_cluster`) rejects: `dimension`'s length not matching what `topology_type` implies (`RING`→1 axis, `TORUS_2D`/`MESH_2D`→2, `TORUS_3D`→3, via `_TOPOLOGY_AXES`); any `dimension` entry `< 1`; `MESH_2D` with `wrap=True` (a mesh is non-wrapping by definition -- a torus can go either way, `wrap=False` on `TORUS_2D`/`TORUS_3D` is fine, it's just a plain grid then); and `FAT_TREE` outright, since it has no coordinate/dimension model yet and nothing could ever place a job on one today. These checks live on `Server`, not as a `Cluster.@validates` (unlike `Node._check_coordinates`, which *is* a real invariant every `Node` must satisfy) -- `topology_type`/`dimension`/`wrap` mismatches are an *admin input* mistake to catch at the `POST /clusters` boundary, not a domain-model invariant every `Cluster` must satisfy everywhere: `Topology`/`TopologyView`'s own math is deliberately generic over any dimension length regardless of `topology_type` (see `CLAUDE.md`), and `tests/domain/test_topology.py` constructs `FAT_TREE`/axis-mismatched/wrap-mismatched `Cluster`s directly, bypassing `Server` entirely, specifically to exercise `Topology`'s own deferred-`NotImplementedError` and wrap-rejection paths. Putting these checks on the model (an earlier pass at this did exactly that) would apply them to every construction path, including those tests, and break them. All of these raise `ValueError`, reusing the same `422` handling `POST /clusters` already had for bad node coordinates. `Topology.__init__`'s own `MESH_2D`+`wrap=True` check stays as a second, cheap guard at placement time, for callers that build a `Cluster` outside `Server.create_cluster`.
- **Exceptions live in `app/domain/exceptions.py`, not scattered across `server.py`.** All ten `Server`-raised exceptions (`InstituteNotFoundError`, `QuotaExceededError`, etc.) moved out of `server.py` into their own module once the file grew past ~500 lines with a third of it being exception boilerplate before the actual `Server` class. Every router imports exception types from `app.domain.exceptions` directly (not re-exported through `server`) so there's one place that owns "what can go wrong," separate from "what `Server` does about it."
- **`GET /clusters`, `GET /clusters/{id}`, `GET /jobs` -- read endpoints for the planned frontend, not wrapped in `BaseOut`.** Every other route in this codebase wraps its response in `detail`/`status_code` (`BaseOut`), but that only makes sense for a single action's outcome -- a list of clusters or jobs is just a collection, so these return a bare list/object with no envelope. `Cluster.total_capacity()`/`free_capacity()` and `Node.resource_summary()` (`app/models/cluster.py`, `app/models/node.py`) are the same "enrich the ORM model directly" pattern as `Node.free_resources()` -- plain Python over `self.nodes`/`self.resources`, not a query, so listing many clusters means one query per cluster's node/resource relationships rather than a single aggregate query. Fine at this scale; revisit if cluster/node counts grow enough for it to matter.
- **Reservation-caused placement failures don't trigger strict-order's stop-the-drain rule; genuine capacity failures still do.** Strict order exists to stop a low-priority job from jumping ahead of a high-priority one just because there's temporarily not enough free capacity for the one at the head of the queue (see above) — that's real contention, and skipping past it would be backfilling. But a job that fails *only* because reservation exclusion narrowed its own institute's view of the cluster (`Placer.has_enough_capacity(job, all_nodes)` says it would fit on the full node set) isn't cluster-wide contention at all — it says nothing about whether some other institute's job, unaffected by that reservation, could run right now. `_drain_queue` tells the two apart with a non-mutating check and only holds the reservation-blocked job aside (re-enqueued after the drain pass, not immediately, to avoid re-dequeuing the same stale entry in a tight loop) instead of breaking. A genuine capacity failure still stops the drain as before. Found via `test_reservation_blocks_other_institutes_but_not_the_owner`: without this, a job blocked purely by someone else's reservation would permanently starve every other institute's queue entries on that cluster, including ones the reservation says nothing about.
- **Row-level locking extended to `create_reservation` and `create_quota` -- the same TOCTOU race `_build_placer`'s `FOR UPDATE` already guards against for placement, just for admin writes instead.** Without it, two concurrent `POST /reservations` for the same node could both pass the conflict check before either commits and both succeed (silent double-booking); two concurrent `POST /quotas` for the same institute/resource_type/month could both see "no row" and both insert (breaking `_check_quota`'s `.one_or_none()` with `MultipleResultsFound` on the next submission). `create_reservation` now locks the target `Node` rows before checking for conflicts; `create_quota` locks the `Institute` row before its upsert lookup (coarser than per-resource_type/month, but quota-setting is infrequent enough that this is an acceptable tradeoff, same reasoning as the cluster-wide placement lock). No DB-level unique constraint backs either up -- the lock is the only thing preventing the race.
- **Added straightforward read/delete endpoints that were simply missing, not because of any design tension:** `GET /jobs/{id}` (full detail incl. `requirements`), `GET /jobs/{id}/events` (the `job_event` rows -- previously write-only, nothing ever read them back), `GET`/`GET /{id}` for `institutes` and `clients`, `DELETE /quotas/{id}`, `DELETE /reservations/{id}` (`Server.cancel_reservation` manually deletes the `NodeReservation` rows first -- no cascade configured on that FK).
- **`ClientStatus` — resolved as a last-activity marker, not true liveness.** `submit_job` flips a `Client` to `ONLINE` the moment it submits a job; nothing ever flips it back to `OFFLINE` (there's no heartbeat/session concept in this REST-only API to hang a timeout off of, so "goes idle after N minutes" is a separate feature, not built). It's one-directional and approximate by design -- "has this client ever been active," not "is it connected right now."
- **Node decommissioning — resolved via `Server.set_node_down`/`PATCH /nodes/{id}/down`, same eviction-vs-wait call as reservations: wait, don't evict.** Its `AVAILABLE` resources flip to `UNAVAILABLE` immediately; any `ALLOCATED` ones are left alone (the running job keeps going) until released, at which point `Placer.release_resource` checks `node.status == DOWN` and releases to `UNAVAILABLE` instead of back to `AVAILABLE` -- otherwise a decommissioned node's resources would quietly become placeable again the moment their job ended. `Node.status = DOWN` is set immediately (not deferred), both as the marker `release_resource` checks and because `_recompute_status`'s existing guard (`if node.status == DOWN: return`) already leaves a `DOWN` node's status alone once set. Locks the `Node` and its `ResourceNode` rows first (`with_for_update`), same reasoning as the other row-locking above. No "bring back up" endpoint yet -- one direction at a time.
- **A job's `requirements` can't repeat the same `resource_type` — rejected at `submit_job`, not just an API nicety.** Found by inspection, not a report: `Placer.place()` keys its `needed`/`remaining` dicts by `resource_type` (`{req.resource_type: req.amount for req in job.requirements}`), so two requirement rows for the same type would silently keep only the last one's amount at placement time -- the job runs under-provisioned with no error. `_check_quota` had a matching bug: it checked each requirement tuple against the same "currently allocated" baseline independently, rather than summing same-type amounts first, so it could pass a combined total that actually exceeds the quota. Nothing enforced distinctness at any layer (schema, domain, or DB) before this. Fixed with one check at the top of `submit_job` (`ValueError` → `422`), not a schema-level `model_validator`, so it also protects any other internal caller of `Server.submit_job`, not just the HTTP boundary.

## Open items (not yet resolved as of 2026-08-01)

- **Multi-cluster placement — fully resolved.** One `Placer`/`Scheduler` per `Cluster` (2026-08-11), and routing a job to a specific cluster is resolved above (best-fit by capacity, `Server._best_fit_cluster`).
- **`dimension`/`coordinates` validation — resolved 2026-08-11.** `Node._check_coordinates` (`app/models/node.py`) validates length and bounds against `self.cluster.dimension` whenever `coordinates` is set.
- **`FAT_TREE` topology — deferred.** `TopologyView.neighbors()`/`.distance()` raise `NotImplementedError` for it; it isn't a coordinate grid (distance would be common-ancestor depth in a switch hierarchy), and `coordinates`/`dimension` have no agreed meaning for it yet.
- **`resource_usage`/`consumed_hours` — unbuilt.** Nothing anywhere writes to this table. `Quota` enforcement (above) is a live concurrency cap, a deliberately separate thing from "how many resource-hours has this institute consumed this month" cumulative tracking, which is what `resource_usage` exists for. Building it needs its own design pass: what counts as consumed (allocation duration × resource count, on completion only or cancellation too?), one row per completion vs. an aggregate running total, whether it resets each month.
- **`FAILED` (`ResourceStatus`) — still unused.** `set_node_down` only ever produces `UNAVAILABLE`; nothing distinguishes "intentionally decommissioned" from "hardware actually failed," and there's still no "bring a node back up" endpoint (one direction at a time).
- **Node `coordinates` — who assigns them, and how, needs its own ticket.** Found alongside the `resource_type` bug above: nothing stops two different `Node`s in the same `Cluster` from getting identical `coordinates` at `POST /clusters` time (`Node._check_coordinates` only checks length/bounds against `dimension`, never distinctness from sibling nodes) — `TopologyView._by_coordinates` would silently let one clobber the other in that dict, breaking `neighbors()`/`distance()` for whichever node lost. That's a real, fixable gap (a straightforward distinctness check in `create_cluster`), but it opens a bigger question worth its own ticket rather than a quick patch: **should coordinates be user-specified (today's design) or auto-generated from `dimension`?**
  - Coordinates aren't arbitrary labels — `TopologyView.distance()`/`neighbors()` treat them as real adjacency, and `PlaceAlgorithm` (Pack/Spread) makes actual locality-aware placement decisions off of that. Auto-generating them "any old sequential assignment reshaped into `dimension`'s shape" would produce a distance metric with no relationship to anything physically real, silently defeating the entire point of the locality-aware algorithms. In a real deployment, coordinates should reflect actual rack/interconnect position, which only whoever is physically racking the hardware would know — arguing for keeping them explicit/user-specified, at least for real (non-demo) clusters.
  - The current design's explicit-coordinates approach already supports **sparse/partial grids** for free (a cluster can be short of its full `dimension` extent — not every logical grid position needs a physical node — since `TopologyView` just looks up whatever's in `self._by_coordinates`, returning nothing for a gap). A "fully auto-generate a dense grid from `dimension`" mode would be strictly less flexible unless it's offered as an *additional* convenience path, not a replacement.
  - `FAT_TREE` is out of scope for any of this either way — it already has no coordinate/dimension meaning (see above), so whatever comes out of this ticket for grid topologies wouldn't apply to it.
  - Minimum fix regardless of that larger decision: reject duplicate `coordinates` within one `Cluster` at `POST /clusters` time — not done yet, held for the same ticket.
